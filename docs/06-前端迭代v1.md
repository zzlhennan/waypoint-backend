# 前端迭代 v1（4 项体验改进）

> 基于开发者本人连续使用 `05-前端页面设计.md` 交付的 HTML 页面后的真实反馈。
> 本文档只记改动方案，不重复 05 的基础设计。

---

## 1. 地名/城市联想（输入辅助）

### 痛点
用户输入"奥森"，后端直接取 `pois[0]`——但奥森有南门/北门/停车场/足球场，用户不知道取了哪个。

### 方案

**后端代理接口** `GET /suggest`：

| 参数 | 必填 | 说明 |
|---|---|---|
| `keyword` | ✅ | 输入框内容（如"奥森"） |
| `city` | ❌ | 城市名（搜 POI 时用，搜城市时不传） |
| `type` | ✅ | `poi`（搜地名）或 `city`（搜城市） |

**行为**：
- 后端调高德 `place/text`，`limit=5`
- 返回候选列表：`[{name: "奥林匹克森林公园南门", location: "..."}, ...]`

**前端交互**：
- 输入框聚焦 + 打字时，**debounce 300ms** 调 `/suggest`（避免每打一个字就发请求）
- **最小长度限制**：输入少于 2 个汉字不触发联想（单字"奥"没意义，省一次请求）
- 弹出候选列表（最多 5 个）
- 键盘上下选择 / 鼠标点击选中
- **用户不选弹窗，直接点搜索 → 后端兜底校验**（city 不存在时返回 400）

**QPS 控制**：
- debounce 300ms：用户连续打字时，只在停 300ms 后发一次请求
- 最小长度 2：单字不触发
- 每个输入框独立控制，不会两个框同时触发

**安全红线**：key 不下发前端，后端代理转发。

## 2. 分类 tab 动态化（结果驱动 + JVM 学习）

### 痛点
静态 tab 只有咖啡相关 7 个分类，用户想搜网吧/餐馆时 tab 帮不上忙。

### 方案

**核心思路**：tab 不是预先定义的，而是**从搜索结果动态提取的**。

#### 2.1 后端流程

```
① 收集候选 POI（各采样点 around 结果，按 id 去重）
② 算每个候选到路线折线的最近距离
③ 硬过滤：到路线 > max-detour-meters（本期调整为 2km，见第 5 节）的丢弃
   ↓
④ 【统计 + 学习在这一步，硬过滤之后、topN 截取之前】
   遍历每个幸存候选 POI：
   ① 提取 type（中文，如"餐饮服务;咖啡厅;星巴克咖啡"）
   ② 提取 typecode（如"050501"，高德 v5 around 响应自带此字段）
   ③ 按二级聚合：取 typecode 前 4 位（"0505"）+ 第二级中文（type.split(";")[1]，"咖啡厅"）
   ④ 学习到 JVM：DictUtils.learn("poi_category", "咖啡厅", "0505")
      - 已存在 → 跳过
      - 不存在 → 录入
   ⑤ 累计该二级分类 count
   ↓
⑤ 按距离排序
⑥ topN 截取：topN 为 null（前端选"全部"）时不截取，否则 limit(topN)
   ↓
⑦ 返回 result（截取后的）+ categories（硬过滤后的全集统计，不受 topN 影响）
```

**关键口径**（已与开发者对齐）：
- **统计时机**：硬过滤之后、topN 截取之前。只统计"确实顺路"的 POI，不把偏离主路 2km 外的分类学进来。
- **count 口径**："全部(35)"= 硬过滤后的候选总数；"咖啡厅(18)"= 这 35 个里有 18 个咖啡厅。**统计基于全集，不受 topN 影响**——topN=3 时 result 只返回 3 条，但 tab 仍显示"全部(35) 咖啡厅(18)"。
- **为什么统计在 topN 之前**：tab 表达的是"这条路上有什么、各有多少"，不是"这次返回了几个"。
- **只在 keyword 搜索（不带 category 过滤）时返回 categories**：
  - 如果本次请求带了 `category=咖啡厅`，后端返回 `categories: null`（前端据此不刷新 tab 缓存，保留第一次 keyword 搜索时的 tab 列表）
  - 如果本次请求不带 category（用户第一次搜索 / 点"全部"tab），后端返回完整 categories
  - **为什么这样设计**：避免用户点 tab 过滤后，tab 列表被"过滤后的小集合"冲掉——tab 是"纯 keyword 搜出来的全景"，过滤后的 result 只是这个全景的子集，不应该反过来改写全景

#### 2.2 DictUtils 改动

**原来**：静态种子 7 个分类，初始化后不变。
**现在**：静态种子 + 动态学习。

```java
public class DictUtils {
    // 静态种子（保留原来 7 个）
    static {
        register("poi_category", "咖啡厅", "050500");
        register("poi_category", "冷饮", "050700");
        ...
    }
    
    /** 动态学习：从结果提取新分类，已存在跳过 */
    public static void learn(String dictType, String label, String value) {
        // 如果 LABEL_TO_VALUE 中已有 dictType → label，跳过
        // 否则写入双向缓存
    }
}
```

**学习时机**：每个候选 POI 都学习，在 topN 过滤前（这样所有候选都参与，不只是最终返回的 3 个）。

#### 2.3 前端展示与过滤

**tab 出现时机**：**搜索后才出现**——不是输入前显示的快捷方式。

```
用户输入"咖啡" → 点搜索 → 后端返回 30 个结果
   ↓
前端渲染结果列表
   ↓
同时渲染 tab：[全部(30)] [咖啡厅(18)] [冷饮店(7)]...
   ↓
用户点"咖啡厅" → 重新请求（category=咖啡厅）→ 返回 18 个结果
```

**为什么不在输入前显示 tab**：
- tab 是"当前结果有什么分类"，不是"我们预设的分类"
- 没搜索就没结果，没结果就没分类
- 用户想搜网吧时，先输 keyword=网吧，搜完 tab 自然出现网吧相关分类

**返回给前端的 categories 只含**：
```json
{ "label": "咖啡厅", "count": 18 }
```
- 不返回 typecode（后端内部翻译用）
- 前端拿到 label 后，点 tab 时**回传 category=咖啡厅**，后端再翻译回 typecode 查询

**前端 tab 渲染**：
```
[全部(30)] [咖啡厅(18)] [冷饮店(7)] [糕饼店(5)]
```

**前端点 tab 行为**：
- 把当前 tab 的 label 作为 `category` 参数，**重新请求后端**
- 后端 `DictUtils.getValue("poi_category", "咖啡厅")` → `"0505"` → 透传高德 `types=0505`

**为什么重新请求而不是前端本地过滤**：
- 因为高德 types 参数是**前缀匹配二级编码**（0505 开头全部返回）
- 前端本地过滤 result 数组，可能漏掉"当前没返回但存在的"该分类 POI
- 重新请求后端 = 用高德原生能力，更准确

#### 2.4 与旧方案对比

| 对比项 | 旧静态字典 | 新动态学习 |
|---|---|---|
| tab 来源 | 硬编码 7 个 | 从结果动态提取 |
| 新分类 | 永远没有 | 用一次就学会 |
| 用户体验 | tab 固定 | tab 跟着结果走 |
| 维护成本 | 手动加分类 | 零维护 |
| 前端过滤 | 重新请求 | 重新请求（后端翻译） |

## 3. 默认方式改为驾车 + topN 支持"全部"

### 3.1 默认方式
- HTML 页面 radio 默认选中"驾车"（原来默认"骑行"）
- 后端 `AlongServiceImpl` 默认值已是 `driving`，不用改
- localStorage 记住用户上次选的方式

### 3.2 topN 支持"全部"

**背景**：tab 已显示"全部(35)"，用户想看完整列表时，topN 下拉应支持"不限制"。

**前端下拉**：
```
Top N: [ 3 ▾ ]
        3（默认）
        5
        10
        全部
```

**传参**：选"全部"时，`topN` 不传（空 / null）。

**后端处理**：
```java
// topN 为 null → 不截取，返回硬过滤后的全部候选
if (query.getTopN() != null) {
    filtered = filtered.stream().limit(query.getTopN()).toList();
}
// 否则不 limit
```

**关键**：topN 只影响 `result` 数组的长度，**不影响 `categories` 的 count 统计**（统计基于硬过滤后的全集，见 2.1）。

**localStorage**：记住上次选的 topN（包括"全部"）。

## 4. 接口返回结构变更

### 原 `/along/search` 返回
```json
{
  "query": {...},
  "result": [...]
}
```

### 新返回
```json
{
  "query": {...},
  "result": [...],
  "categories": [
    { "label": "咖啡厅", "count": 18 },
    { "label": "冷饮店", "count": 7 }
  ]
}
```

**新增字段**：`categories`——当前结果的二级分类统计，按 count 降序。

**返回规则**（防 tab 被过滤冲掉）：
- **本次请求不带 category**（keyword 主搜 / 点"全部"tab）→ 正常返回 categories 数组，前端据此刷新 tab
- **本次请求带 category**（点了具体分类 tab）→ `categories` 为 null，前端只更新 result 列表，tab 保留旧缓存

## 5. 配套调整：硬过滤距离 1km → 2km

`application.yml`：

```yaml
along:
  max-detour-meters: 2000   # 原 1000，调大到 2km，让沿途稍远的店也能进候选
```

**为什么调大**：v1 反馈 1km 硬过滤太严，稍偏离主路但仍顺路的店被丢了。2km 是体感上限。
